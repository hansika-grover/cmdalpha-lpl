# Sentinel

**Early detection of elder financial exploitation, built for LPL's workflow, with a person making every decision.**
Team cmd+alpha · LPL WealthX Hackathon, Infinium '26 (IIIT Hyderabad)

Older Americans reported **$7.75 billion** in fraud losses to the FBI in 2025, up 59% in a year: one complaint every
2.6 minutes ([IC3 2025](https://www.ic3.gov/annualreport/reports/2025_ic3report.pdf)). Firms already have the legal tools
to act (FINRA Rule 2165 holds, Rule 4512 trusted contacts, Senior Safe Act immunity), but deciding *when* still depends on
one person noticing one odd event. Fixed withdrawal thresholds miss small, repeated thefts and flag legitimate large
withdrawals, and the richest evidence, what the client told their advisor, is never read systematically.

Sentinel joins three streams LPL already holds (money movement, account changes and advisor notes), scores every household
each time something happens, and hands the advisor or the Senior Investor Protection team a cited case file before the money
leaves.

All data is synthetic. These numbers show what the method does on a realistic simulated book of business; they are not

## How it works

```
account changes ─┐   Engine A  money movement vs the household's own 12-month baseline (robust z, new payees,
money movement  ─┼─▶ Engine B  account-change sequences (contact change → new bank → withdrawal; new POA → payee match)
advisor notes   ─┘   Engine C  notes reader: Claude extracts FinCEN red flags with exact quotes; injections reported, never followed
                          │
                          ▼
             shallow monotone gradient-boosted fusion, calibrated (isotonic) → score + plain-English reasons with record IDs
                          │
                          ▼
       weekly reviewer budget → advisor queue / pre-release check / specialist queue → case agent (Claude + tools) drafts
       call script, trusted-contact note, escalation memo, APS referral, Rule 2165/2166 deadlines → a person decides
```

* **Scored before money moves.** Every withdrawal request is scored before release, and so is every account change and note.
  Features at a moment use only records before it; a test deletes the future and checks no feature changes.
* **Every claim is cited.** Notes-reader quotes must be exact substrings of the note. Case-file claims must cite a record ID
  that exists for that household. Code rejects anything else; the model is never trusted to police itself.
* **Guardrails in code.** Age is never a model input (fairness is reported by age band). No diagnoses. No draft to a trusted
  contact who may be involved. Nothing is sent or held automatically.
* **Hard rule.** Money moving repeatedly to the trusted contact or a new power of attorney always escalates.

## Run it

Python 3.11+.

```bash
pip install -r requirements.txt
cp .env.example .env            # optional: ANTHROPIC_API_KEY for the Claude notes reader and case agent
make all                        # world → notes → eval → seeds → export → agent → readme
python -m http.server -d web    # open http://localhost:8000
```

On Windows without GNU make, use `mingw32-make all`, or run the steps in the `Makefile` directly. Individual steps:

| Step | Command | Time on a laptop |
|---|---|---|
| Synthetic world (20,000 households, 24 months) | `python -m sentinel.generate` | ~1.5 min |
| Claude notes reader (Batches API, cached) | `python -m sentinel.llm.notes_reader` | depends on batch queue |
| Train, calibrate, evaluate (CIs, leave-one-typology-out, robustness) | `python -m sentinel.eval.run_eval` | ~10 min |
| Repeat on 4 more independent worlds | `python -m sentinel.eval.seeds` | ~25 min |
| Dashboard data | `python -m sentinel.export` | ~2 min |
| Claude case agent for queued households | `python -m sentinel.llm.case_agent` | ~1 min per household |
| Tests | `python -m pytest` | ~1 min |

**Without an API key** everything still runs: the notes engine falls back to a keyword + TF-IDF reader and the case files
to templates, and the dashboard and README say so. Claude outputs are cached by note hash in `sentinel/llm/cache/` and
committed, so the demo works offline once they have been generated.

Models are set by environment variables: `SENTINEL_NOTES_MODEL` (default `claude-haiku-5-5`) and
`SENTINEL_AGENT_MODEL` (default `claude-opus-5-5`).

## The synthetic world

`config/world.yaml` holds every rate and the seed; the same seed reproduces byte-identical files (tested).

* 20,000 households aged 55–95 across 250 advisors with five writing styles; log-normal assets (median ≈ $350k).
* Normal life: monthly withdrawals, RMDs, 1–3 lumpy withdrawals a year (some to new contractors or family), renovation
  instalments, account changes at realistic yearly rates, 2–8 notes a year (15% of households have none).
* **2% of households exploited**, in six typologies with FinCEN loss medians ($33.5k scams, $23.8k theft) and the 80/20
  stranger/trusted-person split. Every signal appears only with some probability; 15% of contact scams come with a
  coached cover story.
* **~1,000 legitimate look-alikes**: home purchases, gifts to family, care-home deposits, moving states (the same shape as an
  account takeover), remarriage, transfers to another firm, trust funding.
* 1% of notes carry prompt-injection text, in scam and normal households alike.
* Labels live only in `data/world/labels/`; the feature code cannot load them (tested).

## Limitations, honestly

* **Generator timing bug, fixed 13 Oct (found by Parth), after we had seen results.** The advisor note about the call
  behind a scam's largest withdrawal, and the note explaining a look-alike (e.g. a condo purchase), drew their own random
  time of day instead of using the event they describe. 22–62% of request notes (by scam type) and 48% of look-alike notes
  landed *after* the event, so they were invisible when it was scored. Notes are now time-stamped from the event itself; the
  households, cases and amounts are unchanged. Averaged over 5 worlds at a 0.25% budget, Sentinel's recall rose from 83.5%
  to 85.5% and look-alike false alarms fell from 29.3% to 27.3% (at 1%: 45.6% to 39.9%); the threshold rule and the
  checklist, which don't read notes, did not change. On the main world alone recall moved down within its confidence
  interval (88% to 81% at 0.25%), which is retraining noise on 80 test cases. Results shifted because the data was
  corrected, not because the model was tuned.
* **Mule-account network: the world is v1 plus one column.** Payees now carry a receiving account / wallet fingerprint
  (`dest_ref`), drawn from a separate random stream (seed + 9001), so every other record, ID, timestamp and note is
  byte-identical to the v1 world (v1 numbers frozen in `results/v1_metrics.json`). 35% of stranger-scam payees pay a mule
  account shared with other victims for ~60 days (`config/world.yaml → exploitation.mule`). That mules are reused across
  victims is sourced (FBI IC3 Elder Fraud Reports 2023/2024; FinCEN Advisory FIN-2022-A002; FBI/FinCEN money-mule
  guidance); the exact share, pool size and lifetime are our assumptions. Large legitimate payees (tax, title, care homes,
  insurers) also share accounts, so "many clients paid this" is not a giveaway on its own. All baselines are re-run on
  the same world, and `ablation_no_network` reports Sentinel without these features.
* **Claude's reading was produced without an API key.** For the finals, Claude Code subagents running Claude Haiku were
  given only the notes reader's exact system prompt, JSON schema and chunks of 40 note texts (no labels, no other files),
  and their output went through the same exact-quote validation as an API response
  (`sentinel/llm/cache/notes_claude-haiku-5-5-subagent.jsonl`). Case files were drafted the same way by Claude Opus
  subagents from pre-computed tool outputs and checked by `validate_case_file`. Claude read a stratified sample of 2,226
  notes (for the reader comparison) and the notes of queued households (for the demo).
* **The risk score uses the keyword reader, not Claude.** Every headline number above (cases caught, false alarms, the
  same-workload comparison) comes from a model whose notes features are produced by the keyword list. Claude is used to
  read the queued households' notes with cited quotes, to draft the case file, and in the reader comparison, which shows
  what it would add. The score switches to Claude only when Claude has read at least 95% of the notes the pipeline
  selects, and without an API key we could not read that many.
* **Plan once we have an API key:** put `ANTHROPIC_API_KEY` in `.env` and run `make notes` (Claude Haiku over the
  cost-controlled note selection through the Batches API, cached by note hash). The evaluation then switches to the Claude
  reader on its own, so we re-run `python -m sentinel.eval.select` (feature blocks chosen again on validation), then
  `make eval seeds export`. Next comes `make agent` (the case agent through the API's tool-use loop instead of
  pre-computed tool outputs) and `make readme`. The subagent cache stays in the repo as a record of what was shown at
  the finals.
* **Reader sample.** Red-flag notes for the reader comparison come from all households, because neither reader is trained on
  notes; the rest of the sample is from test households. It is stratified, not population-weighted, so its precision is
  not the precision on a live note stream. Neither reader finds the planted category in silent-takeover service notes
  (9 notes), which describe the request but no red-flag language.
* **Household memory** uses a first-stage model's score on the household's earlier events; training rows get
  out-of-fold scores, with one exception found in review: the keyword reader's TF-IDF note risk, an input to that
  first stage, is fitted on all training notes, so for training rows it is in-sample. Validation and test are
  unaffected (no test number is inflated), but memory may lean on that score more than it should; we did not refit for
  the finals. Leave-one-typology-out runs drop the two score features (the first stage saw every scam type) and are
  compared with a model on the same features trained on every type. The keyword TF-IDF is still fitted on the held-out
  type's training notes in those runs.
* **Ablations:** household memory is built from money, sequences and notes, so "Sentinel without notes" (and without
  money, without sequences) also drops memory.
* Synthetic data. Advisor notes are template-generated in five styles; real notes are far more varied. The next step is a
  backtest on LPL's past Senior Investor Protection cases, then a silent run alongside today's rules.
* The weekly alert budget is a parameter LPL would set; precision is low at generous budgets and is also reported at a
  realistic 0.5% base rate.
* Personal details are not yet redacted before notes reach the model; in production this would run inside LPL's environment.
* Fairness is checked, not assumed: false alarms are reported by age band against a 1.25× target (see Results), and age
  is never a model input. Older clients more often add a POA or move money to family, which is legitimate, so this needs
  watching on real data.
* With no notes at all, recall holds up but false alarms on legitimate look-alikes rise: the notes engine's main job is
  reading the context that clears a client.
